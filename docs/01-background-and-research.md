## 1. 项目背景

### 1.1 从哪来：原项目 openai-code-review

原仓库 `zingaltern/openai-code-review`（2025-03 创建）是一个 Java 技术栈的代码评审组件骨架：

| 维度 | 现状 |
|---|---|
| 技术栈 | Java 8、Spring Boot 2.7.12、Maven 多模块 |
| 模块 | `openai-code-review-sdk`（核心）、`openai-code-review-test`（验证工程） |
| 核心逻辑 | `OpenAiCodeReview#main`：ProcessBuilder 执行 `git diff HEAD~1 HEAD` 并打印 diff |
| 集成方式 | GitHub Actions：push/PR 到 master → checkout(fetch-depth=2) → `mvn install` → `java -jar` 运行 SDK |
| 完成度 | **仅骨架**。LLM 调用、评审结果结构化、GitHub 评论回帖均未实现 |

原项目的意图很清晰：**CI 触发 → 取 diff → LLM 评审 → 回帖 GitHub**。这条最小闭环思路是对的，但停留在第一步。

### 1.2 到哪去：为什么需要全新项目

2026 年业界共识已经变化，单次"diff → LLM → 评论"的初级形态有三个致命问题：

1. **误报噪声大**——单模型单视角评审，幻觉结论直接污染评论区，开发者很快学会忽略它；
2. **无验证机制**——发现（finding）没有独立复核，"看起来像 bug"和"确实是 bug"不分；
3. **无反馈闭环**——评审质量不可度量、不可回归，prompt 改动全凭感觉。

Anthropic 2026 年发布的内部实践（见 §2）证明了**多子代理并行评审 + 独立验证**是有效方向，并给出了完整方法论。本项目在原项目定位上，按该实践重新设计；其中验证层的具体构造（复核指令、仲裁、异构模型分配）**是本项目的自主设计，无生产背书**，以评测数据作为唯一裁判（见 §3.2 的诚实归属与 06 的门禁设计）。

### 1.3 与原项目的关系（重要约束）

- **演进而非重写**：新项目继承原项目的定位（挂在 Git 平台 CI 上的评审组件）与集成思路（GitHub Actions 触发）；
- **仓库全新**：新项目为独立仓库，**禁止向原 `openai-code-review` 仓库推送任何内容**；原仓库仅作为调研参考；
- **功能超集**：原项目设想的"取 diff → LLM 评审 → 回帖"闭环，是新项目里程碑 M0 的功能子集。

## 2. 核心输入一：Anthropic《Solving Code Review at Anthropic》要点提炼

来源：https://claude.dev/blog/solving-code-review-at-anthropic/（2026 年发布）
**本节仅转述博客原文明确陈述的内容；本项目在其之上的扩展一律标注为"自主设计"。**

### 2.1 问题定义

- Claude 编写了 Claude Code 约 90% 的代码，monorepo 变更量从 ~2,500/天（5 月）暴涨到 30,000+/天（9 月），人工逐行评审不可持续；
- 重新定义问题：不是"是否有人读过这段代码"，而是"**这个风险该由哪一层检查（自动化或人工）来兜住**"；
- 评审从"终点门禁"变为"**伴随式检查**"（类比写代码时的拼写检查）；
- 稀缺资源是**人的时间与注意力**；北极星指标：大部分 PR 最多只需 1 个人参与（甚至只有作者本人），同时 revert 率、事故率作为护栏指标不恶化。

### 2.2 分层流水线架构（本项目架构的蓝本）

1. **Pre-PR 自验证**：作者侧 agent 先跑测试/构建/lint，必须**展示输出而非声称完成**；再用第二个子代理以全新上下文复检 diff。Boris Cherny 估计自验证让结果好 2~3 倍——**这是全流程杠杆率最高的单一机制，本项目据此把它从 M3 提前到 M2**（见 07）；
2. **PR 上的 AI 评审**：
   - **多个 agent 并行找 bug**（博客原文）；
   - **独立的 verifier agent 对每条 finding 投票，只有获得足够共识的才发布**（博客原文；其验证者数量、指令构造、独立性保障等实现细节**未公开**）；
   - 风格/清理类发现经 A/B 测试后被砍掉（噪声大于价值）；
   - finding 以 inline comment 呈现，标注 Important / Nit / Pre-existing，按严重度排序；
   - 每条 finding 必须被修复或给出理由后 resolved；
   - 管理员可按仓库选择 Quick / Standard / Deep 评审深度；
3. **安全评审**：独立的阻塞性 pass，存在未处理安全 finding 则不可合并；后续 commit 修复后自动清除；
4. **强制 CI**：lint、类型、多平台测试、构建；
5. **基于风险的人工审批**：分类器将 PR 分为 Low / Medium（1 人）/ High（2 人）；agent 的批准**永远不算人工批准**；审批绑定具体 commit；
6. **合并队列 + 灰度发布**：对最新 main 重跑检查；先员工 → latest → stable；
7. **快速回滚**：特性开关秒级关闭；事后复盘必问"哪一层本该拦住它"。

### 2.3 让评审者变强：反馈闭环

- **事故即评测集**：历史引发事故的 PR 经专家标注形成评测集，评审系统每天在其上打分；prompt/工具/模型的改动只有分数不降才保留（回归门禁）；
- **噪声度量**：将每条 comment 按人类反应分类（fixed / wrong / intentional / ignorable）；同时对已知干净的 PR 跑评审测误报；
- **收敛控制**（解决 agent 作者与评审者无限循环，曾有 PR 隔夜跑了 50+ 轮）：轮次上限（3 轮后重新考虑方案本身）、后期只对增量 diff 复审、只标记 bug 类别而非逐实例、同一 finding 不重复上报；git blame 显示 ~59% 被标记代码是存量代码 → 引入 Pre-existing 标注；夜间 agent 评审存量代码；
- 效果：6~9 月合并 PR 翻倍且 revert 占比降 40%+；一轮过率 65%→78%，5 轮以上 PR 从 8.9%→1.5%，平均评审轮次 2.08→1.32。

### 2.4 工程规范类实践

- `CLAUDE.md`：只放技术栈、约定、目标/非目标，保持短小；
- **`REVIEW.md` 由代码 owner 撰写**并配合 CODEOWNERS/分支保护——**所有权保护是该机制的承重墙，本项目 v1.0 只抄了文件格式而丢掉了这堵墙，v1.1 修复：REVIEW.md 一律从 base 分支读取**（见 04§3）；
- 重复出现的 finding 在源头修（lint 规则 / skill / 指令文件），而不是在评审里反复提；
- 漏报复盘时问"模型当时缺什么上下文"，然后补进配置/技能/检查项。

### 2.5 人的位置

- 人负责：决定做什么（方向与品味）、高风险代码与架构范式评审、读证据、对结果负责；
- "你合并你拥有"，通过小变更、可逆性、按爆炸半径定审查强度、无责复盘来对冲风险；
- **AI 只发布 finding，不发布批准**——approval 永远是人的决策。

## 3. 核心输入二：业界与学术调研（v1.1 修正归属）

### 3.1 商业 AI CR 工具格局（2025-2026）

| 工具 | 特点 | 对本项目的启示 |
|---|---|---|
| Greptile | 全代码库索引 + 语义检索，擅长跨文件 bug，价格高 | 跨文件上下文是高价值方向，但索引基础设施后置（M4+） |
| CodeRabbit | 免费额度大、平台集成广，但**噪声偏多**是主要抱怨 | 噪声是 AI CR 的头号产品风险，独立验证机制必须前置 |
| Qodo / BugBot | 聚焦测试生成与 bug 专项 | 测试覆盖类 reviewer 作为独立子代理 |
| Graphite / Augment 等 | 均在做"第一道过滤 + 人工聚焦高风险"定位 | 定位一致：AI 做第一道，人做高风险决策 |

### 3.2 学术证据与**域适用性声明**（v1.1 修正）

| 研究 | 原始场景 | 结论 | 对本项目的实际效力 |
|---|---|---|---|
| AEGIS-D（OpenReview） | **数学竞赛答案验证**，非代码评审 | 多 agent 辩论+投票达 92.5% precision，误报降 8.2× | **域错配，仅为"发现/验证分离 + 投票"方向的间接证据**；其误报下降依赖验证者多样性前提，见 03§2 |
| Refute-or-Promote（arXiv 2604.19049） | **C/C++ 缺陷挖掘** | 对抗式、阶段门控评审针对协作辩论漏掉的误报类别 | 对抗式验证的**思想来源**；本项目 M2 简化为平衡式独立复核，纯证伪导向作为 M3 第二验证者的差异化指令，避免系统性拒真 |
| Debate or Vote（NeurIPS 2025） | 通用 LLM 决策 | 投票贡献绝大部分收益，辩论本身收益有限 | **支持简单投票、不支持叠加多轮辩论** → 本项目投票保持简单多数，分歧走一次性仲裁而非辩论循环 |
| Anthropic 内部实践 | 生产代码评审 | 多 agent 并行找 bug；独立 verifier 投票、仅存活者发布 | 投票机制的**生产存在性证明**；但盲评、证伪指令、judge 仲裁**均非博客内容**，是本项目自主设计 |

**v1.0 的错误已修正**：v1.0 曾把"盲评、证伪导向、分歧仲裁"记为有 Anthropic 生产背书，并把 AEGIS-D 当作代码评审证据——均不属实。v1.1 起这些设计点在 03§7 溯源表中明确标注为"自主设计，以评测数据裁判"。

### 3.3 结论：三条设计公理

1. **精确率优先，但有召回护栏**：宁可漏报也不误报，但**不允许零发布**——验收体系必须有绝对召回下限（§4.4），否则五层精确率漏斗会把系统优化成沉默；
2. **隔离产生多样性，多样性产生精确率**：该公理**同样约束验证层自身**——相关性高的验证者投票等价于单个验证者，因此验证者的多样性（模型异构 + 指令差异）是投票机制成立的前提，不满足则退化为单验证者 + 仲裁（见 03§4）；
3. **不可度量则不可改进**：从第一天起就要有结构化 finding、comment 处置追踪和回归评测集；门禁必须容忍 LLM 非确定性（多次运行统计判定）。

## 4. 需求定义

### 4.1 目标（Goals）

- **G1 端到端闭环**：PR 触发 → 多子代理隔离评审 → 独立复核验证 → 结构化 finding 以 inline comment 回帖 GitHub，全程幂等可重放；
- **G2 精确率与召回双向达标**：发布精确率 ≥80%（人工处置中 fixed/intentional 占比）**且** bad-PR 评测集种子缺陷确认检出率 M2 ≥60%、M3 ≥70%（3 次运行多数判定）；
- **G3 可配置**：仓库级 `REVIEW.md` 定义评审规则（**从 base 分支读取，防 PR 作者旁路**）；评审深度 Quick/Standard/Deep 可选；
- **G4 可演进**：模型无关（OpenAI 兼容协议）、平台可扩展（GitHub 先行）、CI/本地/服务三种部署形态共享核心；
- **G5 可观测**：每次评审的完整 trace 落盘可查（CI 形态经 Actions artifact 持久化），状态账本有明确归属（见 02§5）。

### 4.2 非目标（Non-Goals，明确不做）

- 不做自动修复 PR（评审是本项目的全部；修复属于后续项目）；
- 不做人工审批的替代（只输出 finding 与风险分级**建议**，approval 永远是人/平台策略的决策）；
- 不做 IDE 插件、不做全代码库语义索引（M4 之后再说）；
- 不做多租户 SaaS 平台化（先服务好自己的仓库）；
- **M0–M3 只支持 pull_request 触发**（inline comment 依赖 PR diff；push 直推场景的 commit-comment 模式排入 M4，见 05§4）。

### 4.3 关键用户与场景

| 角色 | 场景 |
|---|---|
| PR 作者（主要用户） | 提 PR 前**本地自评审**（pre-PR，M2 提供）；提 PR 后数分钟内收到精确、分级的 inline 评审意见；存量问题被标注 pre-existing 而非甩锅 |
| 仓库 owner / 管理员 | 用 `REVIEW.md` 定制评审策略（变更需 owner 审批）；选择评审深度；查看噪声与精确率报表 |
| 平台 SRE / 架构组 | 部署维护组件；配置模型路由、并发与预算；接入新 Git 平台 |

### 4.4 成功指标（验收口径，v1.1 增加召回护栏）

| 指标 | 定义 | 目标 |
|---|---|---|
| 发布精确率 | 已发布 comment 中人工处置为 fixed / intentional 的比例 | ≥ 80% |
| 误报率 | 人工处置为 wrong 的比例 | ≤ 15% |
| **种子缺陷检出率（召回下限）** | bad-PR 评测集中，种子缺陷被 confirmed finding 命中（位置+断言匹配）的比例，3 次运行取多数 | **M2 ≥60%，M3 ≥70%；任一 bad-PR 样本多数运行零 confirmed 视为门禁失败** |
| **零发布率（沉默护栏）** | 全部评审 run 中 finding=0 的比例 | 监控指标，连续两周趋势上行即触发复盘（区分"代码真干净"与"机制坍缩"，配合覆盖率声明） |
| 覆盖率声明 | Summary 如实声明实际评审的文件范围与裁剪情况 | 100% run 覆盖（声明缺失即验收失败） |
| 单 PR 评审延迟 | 触发到回帖完成 p95（Standard，假设 ≤2k diff 行、≤10 文件） | ≤ 5 分钟 |
| 单 PR 成本 | token 折算成本均值 | 预算硬上限可配置（04§2 算术） |
| 评测集回归 | bad-PR 检出率变化 | 3 次运行均值下降 >2pp 则禁止合并 |

## 5. 技术选型决策

### 5.1 决策矩阵（编排语言/框架）

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Java 17 + Spring Boot 3.x + 自研轻量编排**（选定） | 与原项目及团队技能连续；CI jar 运行方式已验证；agent 核心循环本就轻量，自研可控可测 | LLM 生态不如 Python 丰富 | ✅ 选定 |
| Python + LangGraph/CrewAI | agent 生态最丰富 | 与原项目断裂；结构化 pipeline 易失控 | 备选 |
| TypeScript + Claude Agent SDK | 与 Claude Code 生态近 | 分发重；团队无积累 | 不选 |

**选型原则**：不引入重编排框架。子代理 = "自包含 brief + 有限工具白名单 + LLM 循环 + 结构化输出"。LLM 访问统一走 OpenAI 兼容协议（可路由 GLM / DeepSeek / Qwen / Claude / GPT 系端点），核心流程不绑定框架。

### 5.2 其他关键选型

- **Git 平台**：GitHub（REST API v3），抽象 `GitPlatformAdapter` SPI；**blame 经由 CI checkout 的本地 jgit 实现**（GitHub API 无行级 blame 端点，见 05§2）；
- **结构化输出**：LLM JSON mode / function calling 强约束 Finding schema，Jackson 反序列化 + schema 校验；
- **存储**：**按部署形态区分账本归属**（02§5）——CI 形态以 GitHub 评论为账本 + Actions artifact 存 trace；本地形态 SQLite；服务化形态 PostgreSQL；
- **配置**：仓库内 `REVIEW.md`（**base 分支版本**）+ 部署侧 YAML（模型路由、预算、并发、深度档位）；
- **可观测**：结构化 JSON 日志 + 每次 run 一个 trace（artifact / 本地目录），先不引入重型 APM。

## 6. 风险与对策（v1.1 更新）

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 误报高，用户流失 | 高 | 独立复核前置（03§4）；发布门槛宁严勿松；**但召回护栏同步生效**（§4.4） |
| 验证者相关性导致投票空转 | 高 | 验证者异构前提（模型家族 + 指令模板必须不同，03§2.3）；不满足则单验证者+仲裁（M2 即此形态） |
| 系统性拒真（证伪偏差 × 高门槛） | 高 | M2 采用平衡式独立复核指令；对抗集同时测幻觉与拒真两方向；召回下限门禁 |
| 大 PR 上下文/成本失控 | 高 | 分层上下文按档注入 + 分 chunk + 预算降档阶梯（04§2）+ LLM 并发限流 |
| 不可信输入注入（REVIEW.md/diff/注释中的指令） | 高 | base 分支读取策略 + 定界标记 + 指令层级 + 输出转义 + 注入对抗集（04§3、05§6、06§1.2） |
| GitHub API 限流 / inline 锚定失败 | 中 | 适配器限流重试；锚定逐条校验 + 非法降级 Summary（05§2） |
| agent 循环不收敛 | 中 | 轮次上限、diff-only 复审、指纹去重（03§5） |
| 评测集小导致门禁随机红绿 | 中 | k=3 次运行统计判定 + 容差带（06§1.2） |

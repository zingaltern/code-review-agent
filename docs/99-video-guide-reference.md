# AI 时代 Code Review 方案设计指南（整理稿正文）

> 整理自视频《AI 写得比你读得快，code review 要怎么做？》（约 18 分钟），结合其中引用的 Anthropic 团队公开实践。
> 用途：作为 code review 智能体项目（code-review-agent）的方法论设计输入。文中「案例」均为视频原案例，保留细节以供设计推理时引用。

---

## 1. 核心论点：读代码捆绑了三件性质不同的事

平时说的"读代码 / code review"，实际同时在做三件事。AI 写码的速度把这三件事拆散了，方案设计必须先把它们分解，再用不同机制分别解决——**不要幻想用一个统一的 review 流程同时解决三件事**。

| # | 功能 | 本质 | 性质 | 失效方式 |
|---|------|------|------|----------|
| 1 | **挑错**（double check） | 找 bug、edge case、空指针 | 技术问题 | AI 写码速度 > 人读码速度，人眼逐行找错被 PR 淹没 |
| 2 | **对齐上下文**（cross check） | 改动是否符合全局架构、业务需求、产品历史 | 产品/组织问题 | 关键上下文不在 diff 里，读了也看不出来 |
| 3 | **担责**（sign-off） | 在 PR 上点 approve 即签字，出事有人扛 | 政治/组织问题 | 责任永远在人身上，无法推给 AI |

**三个常见抱怨与三个侧面的对应关系**（这是设计的出发点）：

- "读不过来" → 吞吐量问题 → 功能 1（double check 交给机器）
- "读了也看不出来错" → 上下文问题 → 功能 2（cross check，上下文不在代码里，需要穷尽记忆、tribal knowledge、组里潜移默化的规则）
- "不读就要背锅" → 责任问题 → 功能 3（签字担责的规矩要重定义）

## 2. 功能一：Double Check（挑错交给机器）

### 2.1 核心原则

**人不要重读代码，机器重做一遍。** 比喻：你把工作交给 manager 时，manager 不会把你的活从头重做一遍——那本质是 double check，谁这么干谁迅速成为整个 team 的瓶颈。但对 AI 来说"重新做一遍"特别便宜（基本免费），所以应该交给机器。

### 2.2 设计规则

1. **全新上下文独立复查（fresh context）**：提 PR 前先跑完本地测试，再用一个**全新上下文的子 agent** 做独立复查。为什么必须全新上下文：刚写完代码的 agent，所有信息都在它的 context window 里，思维有惯性，**很容易给自己写的 bug 找理由**——如同财务和审计必须分开，不能自己审自己。
2. **A/B 赛马对账**：同一任务让两个 AI 各自算一遍，派第三个 AI 找差异。两边对得上的基本放心，人只管对不上的地方。（适用报表/确定性输出，也适用于代码。）
3. **PR 后多视角并行 + 交叉投票**：交了 PR 后，让多组 agent 从不同视角并行找问题，再拉一组 agent 交叉投票筛选，只把真问题留下来给人。
4. **设收敛上限，防止 scope expansion**：机器互相挑刺会不收敛——不停挑 edge case、加 guardrail、给小项目不停加 scope 停不下来。解法：**机器 code review 最多改三轮，三轮仍不收敛 = 设计有问题，打回让作者停下来重新设计**（而不是继续改）。
5. **人在这一关的职责是"踩刹车"**：
   - 对 AI 没完没了的 scope expansion 说"不"；
   - 设计让机器先筛好几遍的 mechanism，人只对漏下来的问题做决策。
   - 复杂臃肿没关系——让机器跑好几轮、互相 debate 都可以，只要人有刹车。

### 2.3 案例

- **manager 比喻**：manager 重做下属全部工作 = double check = 迅速成为瓶颈 → 对人不可行，对机器可行且便宜。
- **Anthropic Claude Code 团队三道工序**（第一道即本节）：提 PR 前（本地测试 + fresh context 子 agent 独立复查）→ PR 后（多视角并行找错 + 交叉投票）→ 签字关（见第 4 节）。

## 3. 功能二：Cross Check（对齐上下文，光看代码看不出来）

### 3.1 核心原则

有一类问题 **double check 永远查不出来**——因为破坏它的上下文根本不在 PR 的 diff 里。哪怕把代码读一百遍也读不出来。需要的是 cross check：**从与代码无关的独立角度核对**。

### 3.2 案例：后台会话超时事故（本节核心案例，务必保留全部细节）

某公司依赖 AI 做代码评审和写码，merge 了一个**修改后台会话超时逻辑**的 PR：

- 当时过了 CI/CD；AI 没看出问题，人也没看出问题，approve + merge 上线。
- 上线后发现：**企业客户的数据导出大量 job 挂掉**，尤其是后台任务跑着跑着就中断。
- 排查结论：该代码有一个**隐含假设**——所有后台任务都在一个常规会话里跑完。
- 而 **六周前** 他们上线过一个针对企业客户的特殊定制，正是这个改动 break 了隐含假设。
- AI 当时没发现的原因：六周前的产品改动**不在这个 PR 的 diff 里**。

**推论**：如果给 AI 提供足够 context（内部文档、产品变更记录、历史故障复盘），它是有可能发现的。但前提是这些东西必须是 **document**——如果是 tribal knowledge（记在人脑子里），AI 不会读心，还是看不见。

### 3.3 Cross check 的两种典型手法

1. **Sniff test（数量级直觉）**：报表数字看着挺顺眼，但 manager 一看就知道"数量级不对，跟我的经验不一样"。凭嗅觉闻出问题。
2. **业务背景核对**：知道产品的历史是什么、最近改过什么、上下游动过哪里——看到改动就知道"里头肯定有问题"（正是上面事故案例的情形）。

### 3.4 关键规律：写下来 → 边界外推

> **人的 cross check 一旦写下来，就变成机器的 double check。**

- 今天你凭脑子里的记忆核对六周前的产品 = 人的 cross check；
- 一旦把六周前的产品改动写进文档，下次机器巡检照着查 = 机器的 double check（对机器是确定性工作）。

由此：**人负责的边界不是静态的，随"写下来"不断外推**。AI-native 组织只要持续把东西写下来，就能把越来越多的东西交给 AI，人不必在原地盯细节——把细节写给 AI，AI 替你盯细节。

**组织层面的设计含义**（不仅是技术问题）：

- 组织政策（policy）应要求：**所有决定留档、写成文字、写在明面上**；
- 不要把决策藏在 Slack 私信（非 channel）或没有记录的会议里——AI 看不见的东西会导致 AI 出错。

## 4. 功能三：担责（approve 即签字）

### 4.1 为什么这一关永远推不给人以外

出了事总得有人对业务、对客户负责。道歉时不能把 AI 推出去；机器/agent 也无法在 postmortem 上"我来赔钱 / 我来降职扣钱"。

### 4.2 Anthropic 在签字关定的三条规矩

1. **Agent 不算 code review approver**——不管多少个模型双手赞成，都不能代替人类签字；
2. **approve 只对特定 commit 有效**——只要 AI 提交了另一个 commit，必须重新再看；
3. **指挥 agent 写代码的人，自己必须在签字名单上**。

### 4.3 签字含义的转变（设计文档里要明确写出的语义变更）

- 以前：签字 = "彻底研读过这几百行代码，觉得没有毛病"；
- 现在：签字 = "我核实过这次代码改动的**意图、假设、设计**，都核对过了，没有问题，上线吧"。
- 配套做法（Anthropic 把 Git 重写为 **Scion**，agent 用的 high-throughput git）：不逐行读 AI 的实现，从更高层核对——这个改动想干什么？设计符不符合惯例？会不会碰到奇怪的 corner case？
- **底层实现对不对，交给测试、交给仿真——那不是人干的事情。**

### 4.4 规模化的配套：风险分级 + 工程兜底

人的注意力有限（Anthropic 的 monorepo 每天约 3 万个变更），所以做了**签字分级**：

| 风险等级 | 内容 | 要求 |
|----------|------|------|
| 低风险 | 纯文档、功能开关 | 测试全过 + 作者在可信名单 → 免签直接上线 |
| 中风险 | 常规业务逻辑、系统提示词（敏感） | 1 人签字 |
| 高风险 | 核心高危路径（经常挂的）、关键配置（难恢复的） | 2 人签字 |

**工程系统兜底**（机制的前提）：

- 至少能**快速回滚**——否则"少审一些代码"的 SLA 承诺不成立；
- Scion 甚至不让每个 PR 排队等 CI 跑完：**先 merge，挂了再用二分法找到改动并撤回**。

### 4.5 效果数据（四个月，Claude Code 这个 repo）

- 合入的 PR 数量：**多了一倍还不止**；
- 合入后需要回滚的比例：**反而降了 40%**。

## 5. 马上能做的四件事（视频结尾的落地清单）

1. **Evaluation first**：把活派给 AI 之前，先把**验收标准写下来**——先想清楚什么叫做"对了"。这是核心价值，AI 没法代替。
2. **Fresh context 审查**：不让刚写完代码的 AI 审自己；新开 fresh context 的 sub agent 或新 job，或者双 AI 赛马各自算一遍看能否对上。
3. **构建自己的 Sniff Test Set**：对经常干的活，故意想"这个东西看着对不对、常见 pattern 是哪些"。例：看报表主要看哪两张表口径对不对；看代码时故意埋一个特定输入看它会不会挂。
4. **先兜底再减负**：检查 CI/CD 交付流程（代码、配置），保证出了问题能**快速回滚**；报表同理——先给小范围的人看、能迅速改正。有了兜底之后，再逐渐减少逐行阅读式 code review。

**长期效果**：做起来之后人负责的边界持续外推（每次把核对经验写下来，下次机器就能用）。但不管边界推多远，**三样东西始终必须由人负责**：

1. 动手之前搞清楚什么叫"正确"；
2. 交付时签上自己的名字，背锅；
3. 把还没写下来的规则、直觉，继续写下来。

## 6. 对 code-review-agent 设计的映射（设计指导）

> 本节把上述方法论映射到本项目。v1.2 设计文档覆盖情况：

### 6.1 已覆盖 → double check（功能一）

- 隔离 reviewer 子代理 + 独立复核 verifier ≈ "全新上下文的子 agent 独立复查"（2.2 规则 1）；
- M2 保留 2 视角并行 BugHunter ≈ "多视角并行找错"（2.2 规则 3 的前半）；
- pre-PR 本地自评审 ≈ "提 PR 前先本地测试再复查"（2.3 Anthropic 第一道工序）。

**可借鉴补强**：

- "approve/结论绑定 commit id，新 commit 必须重审"（4.2 规则 2）→ 账本指纹与 commit 级幂等闸的语义基础；
- "三轮不收敛即打回重设计"（2.2 规则 4）→ 可作为 reviewer↔fixer 循环的 gate 规则，防止 scope expansion。

### 6.2 设计空白 → cross check（功能二，v1.2 未覆盖）

v1.2 所有子代理的输入都是**代码**（diff / hunk 窗口），缺"非代码角度"的核对。若未来增加评审角色，应是 **cross-checker** 类：

- **输入不是 diff 本身**，而是：调用方变更史、产品事件史（近 N 周的产品定制/开关变更）、上下游近期改动、历史故障复盘索引；
- 核对方式对应 3.3 两种手法：
  - 数量级/口径 sniff test：需要预置的 sniff test set（3.3 手法 1 + 5.3 第三件事）；
  - 隐含假设核对：从"本次改动隐含的假设"出发，检索这些假设近期的破坏事件（案例 3.2 的模式：会话超时假设 vs 六周前企业定制）；
- **数据依赖**：cross-checker 的效果取决于产品变更记录是否为结构化文档——印证 3.4 的组织要求"决策留档"，也呼应账本设计中"把核对经验写进文档/账本"的方向（写下来 → 边界外推）。

### 6.3 已有原则性立场 → 担责（功能三）

- AI 只发 finding、不发 approval ≈ 4.2 规则 1（agent 不算 approver）；
- 可进一步吸收：approve 绑定 commit（规则 2）、签字语义 = 核实意图/假设/设计而非逐行读过（4.3）、按风险分级决定评审深度（4.4 表 → 可映射为 review 深度/verifier 档位分级）；
- "先 merge 后二分回滚"（4.4）依赖快速回滚兜底，对应 5.4 第四件事——评审减负的前提是交付系统可快速恢复。

### 6.4 评估设计引用

- Evaluation first（5.1）与项目已有的"召回下限 + 零发布护栏 + Wilson 聚合门禁"一致：先定义"什么叫做对"，再谈自动化；
- 评测集（Defects4J 双侧数据）承担的角色 = 把"什么算真 bug"写下来（3.4 规律的评测版）。

## 7. 反模式清单（设计时对照避免）

1. 幻想一个统一 review 流程同时解决挑错/上下文/担责三件事（第 1 节）；
2. 让刚写完代码的 agent 审自己（2.2 规则 1）；
3. 无上限的 agent 互相挑刺循环（2.2 规则 4）；
4. 期望"读 diff 一百遍"发现上下文类缺陷（3.1、3.2 案例）；
5. 把关键决策留在私信/无记录会议里，然后期待 AI 能核对到（3.4）；
6. 在没有快速回滚兜底时削减人工审查（4.4、5.4）；
7. 把 agent 的赞成票当作签字（4.2 规则 1）。
